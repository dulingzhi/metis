## A. 上游与产品语义

### A1. `--mode=append` 被静默忽略
- **现象**：用户写 `--mode=append`，程序按默认 `replace` 跑，没有任何提示。
- **原因**：旗标解析器只认 `--name value` 空格形式。
- **规则**：旗标解析必须同时支持 `--name value` 与 `--name=value`，并有**两种形式的测试**；
  未知旗标要报错，不能默默忽略。

### A2. 把"配置写入成功"说成"已经生效"
- **现象**：用户保存后以为当前会话变了，实际要重开。
- **原因**：把磁盘状态当成运行时状态。
- **规则**：报告结构里 `written` 与 `runtimeConfirmed` 是**两个字段**；apply 永远不把后者置真；
  界面文案必须区分"已写入 / 下一轮生效 / 需新会话"。

### A3. 摆了一个点了没反应的开关
- **现象**：界面上能开某条通道，点了什么都没发生。
- **原因**：没有先判定"这家能不能用这条通道"。
- **规则**：通道能力只在 `metis-harness` 一处判定，返回 `{ok, why}`；不可用时**界面不提供开关**，
  只显示 `why`。每个 `why` 有测试。

### A4. `off` 不是"卸载"
- **现象**：用户以为 `--mode off` 一次就等于全撤了，磁盘上还留着常驻内容。
- **原因**：单次启动的 `off` 与全局暂停/撤销是三种不同范围。
- **规则**：三种范围在命令名、文案、报告里都必须不同；`off` 时若检测到磁盘上仍有常驻/项目内容，
  **报错并让用户先 `pause`**，而不是默默继续。

### A5. 旧插件在 `off → on` 之后"复活"
- **现象**：关掉又打开，某个旧会话仍按旧人设注入。
- **原因**：插件按回合读取，无法区分"这是新的开启"还是"旧的残留"。
- **规则**：`off → on` 时重新生成 epoch（全局一个、每家一个）；插件每回合核对 epoch，对不上就不注入。

### A6. DSH 的 `/purge` 被当成注入手段
- **现象**：只装 `slash` 通道，以为就能改系统提示词，结果没有效果。
- **原因**：`/purge` 只是开关，真正注入靠常驻插件。
- **规则**：开 `slash` 时若 `install` 未武装，级联安装；界面上写明"这条命令只是开关"。

### A7. 把 user 层当能力
- **现象**：给 `claude` 的 `CLAUDE.md` 写了人设，身份没变。
- **原因**：那是 `<system-reminder>` 上下文块，压不住系统提示词。
- **规则**：只把 `sys` 层算作可用能力；`user` 层落点标为不可用并说明原因
  （`HARNESS-MATRIX.md` 的层列是唯一真相）。

### A8. 以为纯 Rust 就不用写 JS
- **现象**：动手之后才发现 `slash` 通道和部分 `install` 通道要求宿主加载的是 **JavaScript/TypeScript 源码**
  （pi/omp 的扩展、opencode v1/v2 的插件、DSH 的 cordis 插件）。
- **原因**：把"我们用 Rust 重写"理解成"产物里不再有 JS"。
- **规则**：Metis 不运行 JS，但**必须生成 JS/TS 产物**。这些产物是本仓库自己的模板资产
  （`include_str!`），有 golden 测试；模板里的占位符只允许几个（数据目录、人设快照路径、模式、epoch）。
  这是移植里最重、最容易漏的一块，排期时不要低估。

### A9. 以为磁盘格式可以"半兼容"
- **现象**：既想用自己的标记，又想能撤销上游留下的写入 —— 结果两边都不成立。
- **原因**：托管块标记既是注入产物也是磁盘契约，改一个字符就认不出来。
- **规则**：这是要拍板的决定（`PARITY.md` §8 第 7 条）。在拍板之前，**算法集中在两个函数里**
  （标记生成、账本 id 计算），保留可切换的常量，别把哈希与标记散落到十几个文件里。
  拍板"不兼容"就要同时交付"检测到上游残留块并报告"的路径，不能让用户卡在中间态。

### A10. `replace` 在五家上其实是 `strict`
- **现象**：用户以为 `replace` 会保留宿主说明，结果全被换掉了。
- **原因**：`codex`/`claude`/`grok`/`codebuddy`/`hermes` 的启动入口没有读取宿主提示词的通道。
- **规则**：这五家在 `replace` 下必须显式提示"实际按 strict 执行"；有测试断言这条提示出现
  （见 `HARNESS-MATRIX.md` §4）。

## B. 磁盘与恢复

### B1. 无条件独占交换把第二个会话挡在门外
- **现象**：常驻插件每次启动都和 journal 打架，第二个会话起不来。
- **原因**：磁盘内容已经与目标一致时，仍然新建 journal 并独占。
- **规则**：写入前先比较内容，**已一致就直接返回"无事可做"**，不加锁、不建 journal。

### B2. 恢复时覆盖了用户在测试期间的修改
- **现象**：用户手工改了配置文件，程序回滚时把它盖掉了。
- **原因**：回滚只按"这是我写的"判断，没核对当前内容。
- **规则**：回滚前比对当前哈希；既不等于 `beforeHash` 也不等于 `afterHash` → **报冲突、保留 journal、
  保留备份**，什么都不写。

### B3. 失败路径把恢复材料删了
- **现象**：一次失败的撤销之后，用户再也回不到原状。
- **原因**：`finally` 里清理备份。
- **规则**：任何失败路径都不得删除 `backups/` 与 journal；只有成功还原后才销账。
  这条有专门的不变式测试（`ARCHITECTURE.md` I4）。

### B4. 一个持久化文件两个写入者
- **现象**：`state.json` 出现半新半旧的内容。
- **原因**：两个模块各自读改写。
- **规则**：一个文件一个写入者（`state.json` 只由 engine、账本只由 fs、宿主配置只由 channel）。

### B5. 路径大小写导致"同一文件两笔账"
- **现象**：Windows 上同一个文件被记成两个所有者，撤销时漏掉一笔。
- **原因**：路径没有规范化。
- **规则**：所有者键用规范化后的绝对路径；Windows 转小写。测试里必须有大小写不同的两条路径指向同一文件。

### B6. 托管块标记出现在行中间被误吞
- **现象**：删除托管块时把用户后面的内容一起吃掉了。
- **原因**：用的是子串匹配而不是"整行相等"。
- **规则**：只有去掉行尾换行并 trim 后**与标记完全相等**的行才算边界；找不到结束标记时保守处理，
  绝不扩大删除范围。

### B7. 配置文件损坏时"帮忙修复"
- **现象**：程序把损坏的 `state.json` 重命名/覆盖，用户丢了数据。
- **原因**：想"自愈"。
- **规则**：损坏 → **原字节一个都不改**，报错并给路径。恢复由用户决定。

### B8. 撤销方式是个字符串，没人穷尽匹配
- **现象**：某个模块写入了一种新的 `undo.type`，清理逻辑不认识它 → 清理直接抛错、账本被迫留下，
  用户既撤不掉也删不得。（基线上真实存在：`file-stash` 没有被 `reverse()` 认识。）
- **原因**：`undo.type` 是自由字符串 + `if` 链。
- **规则**：`undo.type` 是**封闭枚举**，匹配穷尽；加一种撤销方式必须同时加实现与测试；
  遇到不认识的值 → 报错并保留账本，绝不猜测、绝不丢弃。有一条"未知 undo 类型"的测试。

### B9. 破坏性操作没有闸门
- **现象**：数据目录被算成了 `C:\` 或用户主目录，`self-uninstall` 把整个家目录当成自己的数据删了。
- **原因**：没有校验解析出来的路径是不是"合理的数据目录"。
- **规则**：删除类操作在**建锁、写状态之前**先过闸门（见 `ARCHITECTURE.md` §7.3）：
  数据目录不得是主目录、临时目录或其上级，不得是盘符根/分隔符根，basename 不能为空；
  cwd 在数据目录内也要拒绝。有对应的单元测试（每个拒绝条件一条）。

## C. 进程与平台

### C1. 子进程停在交互提示上，界面卡死
- **现象**：启动某个 harness 后没有任何输出，进程一直挂着。
- **原因**：继承了 stdin，对面在读输入。
- **规则**：stdin 默认关闭或接管道，**绝不继承**；每次执行都有墙钟 + 空闲双截止时间。

### C2. 超时杀了父进程，孙进程还在跑
- **现象**：进程管理器里残留一堆子进程。
- **原因**：只杀了直接子进程。
- **规则**：Unix 用进程组、Windows 用 Job Object；超时/取消/drop 三条路径都必须终止整组。
  有专门的测试（假可执行文件 sleep 后检查残留）。

### C3. `kill()` 之后进程还活着
- **现象**：以为杀掉了，端口还占着。
- **原因**：`kill()` 只是发出请求。
- **规则**：杀进程之后要**等待它真的退出**；测试断言"等待超时后仍然存活"这条路径也行为正确。

### C4. 长内容塞进命令行参数
- **现象**：Windows 上报"命令行太长"（约 8191 字符上限，进程级上限约 32767）。
- **原因**：人设正文（10K 量级）当参数传。
- **规则**：长内容走**文件或 stdin**。基线在 `pi` 上就是踩了这条才改成扩展注入的。

### C5. 输出没有排空，管道填满后死锁
- **现象**：子进程卡住，父进程也在等。
- **原因**：没有持续读 stdout/stderr。
- **规则**：独立线程排空，并有上限（stdout 16 MiB / stderr 1 MiB / 单行 16 MiB），超限只留头尾并标记截断。
  **按记录边界截断**，不要按行切结构化输出（会切碎 JSON/JSON-RPC）。

### C6. TOML/JSON 值没有正确转义
- **现象**：`codex -c model_instructions_file=...` 解析失败。
- **原因**：含空格/引号/换行的值没有包成合法 basic string。
- **规则**：往结构化配置里写值，必须用该格式的**正确转义**；有条目级测试（含空格、引号、换行、反斜杠）。

### C7. Windows 的 `.cmd` 垫片找不到
- **现象**：明明装了命令，启动报"找不到可执行文件"。
- **原因**：只按 `.exe` 查找。
- **规则**：按 `PATHEXT` 查找；路径解析集中在一处（`metis-paths`），有 Windows 专属测试。

### C8. 单文件上限被忽略
- **现象**：写进 `grok` 的人设被静默截断。
- **原因**：不知道对方有 10000 字符上限。
- **规则**：每家落点的约束写进能力表（数据，不是 `if`）；超限时主动截断**并附说明行**，
  同时在报告里告诉用户"被截断了"。

### C9. Windows 上改 PATH 用了 `setx`
- **现象**：用户环境变量被截断（>1024 字符），或者路径里的单引号把脚本搞坏。
- **原因**：`setx` 有长度限制，且拼命令行时没有正确转义。
- **规则**：用 `[Environment]::SetEnvironmentVariable(..., 'User')`；参数手工加单引号转义，
  **不要**用 JSON 序列化去拼 PowerShell 参数。凡是把用户路径拼进脚本的地方都要有转义测试。

### C10. 启动桌面窗口时黑屏/白块
- **现象**：用 `--app` 方式开窗口，出现一块白的。
- **原因**：进程创建时用了隐藏窗口的标志。
- **规则**：需要显示窗口的进程 **必须**允许显示窗口（基线上这是一个真实 issue）。
  默认隐藏只用于后台短命令。

### C11. 杀进程树用了 `taskkill /pid N /F`
- **现象**：宿主退出了，它拉起来的子进程还在。
- **规则**：Windows 上用 `/T`（整棵树）＋ `/F`；Linux/macOS 用进程组。
  **跨平台统一走 `metis-process`**，别在业务代码里各写一份。

### C12. 把用户可执行文件的参数原样透传
- **现象**：未知参数注入了 `.cmd`/`.bat`，出现莫名其妙的解析错误甚至命令注入。
- **规则**：透传给批处理包装器的参数要有**白名单字符集**与**行长上限**（基线用
  `/^[a-zA-Z0-9_./:\\=+,-]+$/` 与 ≤7000）；超长/非法字符的输入走文件或 stdin。
  PowerShell 用 `-EncodedCommand` 传参，并给参数总量设上限。

## D. 界面（egui / eframe）

### D1. 在帧里做慢操作
- **现象**：界面卡住几秒，点不动。
- **原因**：在 `show()` 里扫了 PATH / 读了大文件 / 等了进程。
- **规则**：慢操作一律进后台任务表；取快照用非阻塞接口，拿不到就沿用上一帧。

### D2. 每帧都请求立即重绘
- **现象**：应用空闲时 CPU 也跑满，笔记本风扇转。
- **原因**：用了每帧 `request_repaint` 的 spinner。
- **规则**：自己实现进度指示；有任务时 100ms、构建类 1s、空闲不重绘；加一条源码扫描测试禁止
  使用会每帧重绘的控件。

### D3. 异步结果乱序覆盖新数据
- **现象**：快速切两次人设，界面显示的是第一次的结果。
- **原因**：没有请求序号。
- **规则**：每个异步请求带自增请求号，回来时对不上就丢弃。

### D4. 测试用固定帧数等异步
- **现象**：CI 上偶发失败，本地重现不了。
- **原因**：`run_steps(n)` 在慢机器上不够。
- **规则**：等异步用 `wait()`（等待条件成立），不用固定帧数。

### D5. 影响全进程状态的测试污染其它用例
- **现象**：单跑通过，一起跑失败。
- **原因**：改了渲染后端 / 全局环境变量。
- **规则**：这类用例放**独立的测试可执行文件**；需要子进程就重跑自己并注入隔离的数据目录。

### D6. `ctx.open_url` 静默失效
- **现象**：点文档链接没反应，也不报错。
- **原因**：workspace 关掉了 eframe 的默认 feature，没打开 `links`。
- **规则**：依赖 feature 旗标以最小集为起点时，**每个被用到的能力都要显式打开并写注释说明**。

### D7. 表格/列表错位
- **现象**：长列表滚到后面行高不对，点击命中错行。
- **原因**：手绘行时没算 `item_spacing`。
- **规则**：虚拟化手绘行必须把 `item_spacing` 算进行高；有专门的行高测试。

### D8. 在绘制中读盘
- **现象**：界面偶发卡顿，日志里出现 IO 错误。
- **原因**：`show()` 里读了文件。
- **规则**：UI 只读内存快照；读盘由命令在后台完成。

## E. 测试

### E1. 测试碰了真实用户目录
- **现象**：跑一次测试，用户的真实配置被改了。
- **原因**：用了真实 `$HOME`。
- **规则**：一律经 `metis-testkit::TempHome`；CI 里加一条"真实 HOME 只读"的断言（跑完比对哈希）。

### E2. 只断言 `is_ok()`
- **现象**：测试通过，功能是坏的。
- **原因**：没断言具体值。
- **规则**：禁止只断言成功；必须断言具体字段/字节/退出码。

### E3. 测试自己算期望值
- **现象**：改了实现，测试跟着"自动通过"。
- **原因**：期望值来自被测代码。
- **规则**：期望值必须是人写的常量或 golden 文件。

### E4. 需要真机的用例留在默认 CI
- **现象**：CI 时红时绿，没人信了。
- **原因**：依赖本机装了什么。
- **规则**：真机用例 `#[ignore]` + 在 `docs/TESTING.md` 登记；默认 CI 只跑离线用例。

## F. 文档与流程

### F1. 文档里的数字会漂移
- **现象**：文档说版本 2、代码是 3；四处工具数各不相同；`NOTICE` 列了不存在的字体。
  （参考项目里真实存在这四处。）
- **原因**：手写重复数字。
- **规则**：能被机器核对的数字就写成检查（`cargo xtask ci`），不要靠人同步。

### F2. 规则只写在聊天里
- **现象**：同一个错误反复出现，因为"上次说过了"。
- **原因**：知识留在会话里，没落文档。
- **规则**：能被机器检查的 → 写成 `xtask` 检查；不能的 → 写进本文件。**两者都没有 = 规则不存在。**

### F3. 把"计划"写成"已完成"
- **现象**：`STATUS.md` 说能用，实际跑不起来。
- **原因**：状态列和代码脱节。
- **规则**：`STATUS.md` 的每条"能做什么"必须能指出代码位置与测试名；没有就写"未实现"。

### F4. 顺手重构扩大了 PR
- **现象**：PR 变得无法 review，回归风险上升。
- **规则**：一个 PR 一条路线图条目；发现别的活就加一条 `- [ ]`，不在本 PR 里做。

## G. 落地时真踩到的（M0–M2 期间，按发生顺序）

> 这些不是推演出来的，是写代码时真的撞上并修掉的。每条都附了对应的回归测试。

### G1. `new()` 调用 `default()`，`default()` 又调用 `new()`
- **现象**：`Commands::default_set()` 一调用就卡死；37 个测试集体挂起 60 秒以上。
  第一反应是"某个锁死锁了"，查了半天锁，其实是栈被递归打穿。
- **原因**：`impl Commands { fn new() -> Self { Self::default() } }` 和
  `impl Default for Commands { fn default() -> Self { Self::new() } }` 互相调用。
- **规则**：`new()` 与 `default()` 只能有一个方向。`new()` 直接构造，`default()` 转发到 `new()`。
  **测试里出现"集体挂起"而不是"集体失败"时，先怀疑无限递归，再怀疑锁。**

### G2. `static` 里放不下 `Vec`
- **现象**：注册表写成 `pub static SPECS: &[Spec] = &[...]`，编译报一堆
  `Box::<T>::new_uninit is not yet stable as a const fn`——看起来像编译器 bug。
- **原因**：`Spec` 里有 `Vec`，无法在常量上下文构造；错误信息指向的是 `Box`/`Vec` 的内部实现。
- **规则**：含 `Vec`/`String` 的表一律用 `static X: LazyLock<Vec<T>>`，对外暴露 `fn all() -> &'static [T]`。
  测试里不要再写 `SPECS.len()`，走 `all().len()`。

### G3. 悬空的重构让测试挂住，而不是失败
- **现象**：`egui_kittest` 的 `harness.run()` 在测试机上无限转（CPU 100%），没有任何输出。
- **原因**：它启用了 `wgpu` 却没跑起来（没有可用显示设备）。这类"需要 GPU 的测试框架"
  在没有显示环境的机器上不是失败，是**挂住**。
- **规则**：UI 测试**不引入需要渲染后端的东西**。Metis 的做法：直接用
  `egui::Context::run_ui(raw_input, ...)` 跑一帧，零 GPU、零窗口。见 `crates/ui-egui/src/screens.rs` 的测试。

### G4. `TexturesDelta` 没消费，Drop 时 panic
- **现象**：无头渲染测试全部 panic：`Dropped TexturesDelta with 1 unapplied deltas`。
- **原因**：egui 要求调用方"消费"纹理增量；测试里没有渲染器，增量没人要，Drop 就炸。
- **规则**：无头跑帧之后，显式 `output.textures_delta.clear()`。这不是 hack，是那个 API 的契约。

### G5. `clippy.toml` 的 disallowed 规则需要"显式例外"
- **现象**：`layers` 与 clippy 拦住 `metis-process` 自己的 `std::process::Command::new`、
  `metis-fs` 锁实现里的 `std::sync::Mutex`。
- **原因**：规则写的是"只有 X 可以用"，但 X 自己也被规则扫到了。
- **规则**：例外必须在**代码里**写明并附理由：
  ```rust
  // 本文件是外部进程的唯一入口，允许直接使用 std::process::Command。
  #![allow(clippy::disallowed_methods)]
  ```
  同时 `xtask layers` 的路径判断要按**crate 目录**匹配，不是按包名字符串匹配——
  `crates/process/src/run.rs` 里根本没有 `metis-process` 这个词。

### G6. "暂停"只改了状态，没改磁盘
- **现象**：`metis pause` 后 `state.json` 是 `off`，但 `~/.codex/config.toml` 里的块还在。
- **原因**：`SetPower` 只写了 state，没调 `apply`。
- **规则**：**任何改变"该不该注入"的命令都必须立刻 `apply`**。状态与磁盘不能各走各的。
  对应测试：`pausing_works_even_without_any_persona`、端到端 `mode_and_power_round_trip_through_the_cli`。

### G7. `disarm` 留下了撤不掉的残留块
- **现象**：`metis disarm codex` 之后 `armed` 空了，但配置文件里的块还在，账本里还记着。
- **原因**：`SetArmed` 只改了 `armed` 数组，没有撤下已经写到磁盘的内容。
- **规则**：**关闭一条通道 = 撤销它的落点**。关之前先记下武装过哪些，关之后逐个 `revert`。
  对应测试：`arm_then_disarm_updates_state`，以及真实文件上的手工验证（块消失、账本归零）。

### G8. 暂停必须允许"没有人设"
- **现象**：`metis pause` 在空配置上失败："没有可用人设，无法应用"。
- **原因**：apply 里"注入模式必须有人设"的检查没有排除 `off`。
- **规则**：`mode == off` 的语义是"把东西撤下来"，**反而不需要人设**，而且必须在没有人设时可用。
  对应测试：`pausing_works_without_any_persona`。

### G9. `--channel nope` 被静默忽略
- **现象**：`metis arm codex --channel nope` 退出码 0，实际开了三条通道。
- **原因**：CLI 把 `channel` 数组原样透传，引擎用 `filter_map(Channel::parse)` 丢弃了非法值，
  于是"空列表"被解释成"没给通道 → 默认三条"。
- **规则**：**旗标解析失败必须报错，绝不静默降级**。`filter_map` + 默认值是一个危险组合：
  它会把"用户写错了"变成"用户没写"。对应测试：`unknown_channel_fails_with_code_2`。

### G10. 退出码分类跟"用户传错"混在一起
- **现象**：`metis use ghost`（名字不存在）返回 1，脚本无法区分"参数错"与"执行失败"。
- **原因**：错误类别用错（`PersonaMissing` 是运行时故障，不该用于"名字打错了"）。
- **规则**：退出码由**错误类别**决定，不由文案决定：`InvalidArgument` / `Unknown*` /
  `UnsupportedChannel` / `PersonaInvalid` / `Refused` → 2；其余 → 1。
  "名字不存在"属于调用方传参问题，用 `InvalidArgument`。

### G11. JSON 字段"还原"不等于"原样"
- **现象**：改 `settings.json` 的某个字段再撤销，内容语义对但字节不同（键顺序、缩进都变了）。
- **原因**：`serde_json` 重新序列化整份文档，格式信息全部丢失。
- **规则**：需要**逐字节**还原的写入，必须同时保存原文件字节（`backups/<hash>.bak`），
  撤销时整份写回。只把字段值改回去不叫还原。对应测试：`json_field_round_trips`。

### G12. 块切除时的换行风格会被改掉
- **现象**：CRLF 文件切除托管块之后变成 LF，逐字节比对失败。
- **原因**：切除后统一补了 `\n`。
- **规则**：切除后的收尾换行要**跟随块前面的内容**（含 CRLF 就用 CRLF）。
  对应测试：`crlf_is_preserved`、`mixed_newlines_strip_back_to_the_original_exactly`。

### G13. 生成的 JS 语法对，但语义错——只有跑起来才知道
- **现象**：`slash` 产物用 `node --check` 全部通过，但一装上就注入错内容：
  模式判断反了、重复调用越叠越多、读不到配置时把宿主搞崩。
- **原因**：`--check` 只验证语法。宿主真正关心的是**运行时行为**。
- **规则**：**生成的代码必须有行为测试**，不能只做语法检查。
  Metis 的做法：把运行时的真实函数用 node 跑一遍（`runtime.behaviour.mjs`，34 条断言），
  覆盖四种模式、九步激活、幂等、以及"状态文件损坏就降级为不注入"。
  这些断言由 `cargo test` 通过 `node` 执行，是 CI 的一部分。

### G14. 生成的代码里"重复应用"会越叠越多
- **现象**：同一段 system 提示词每轮都被再追加一次人设，几分钟后变成几百份。
- **原因**：宿主把**我们改过的结果**在下一轮又交回来，我们按"看起来一样"再改一遍。
- **规则**：改写必须带**来源记录**（before → after 的对应表）：下一次先还原成 before，
  再重新算。同一个 after 对应两个不同 before 时标为歧义，**歧义就不动**。
  对应断言：`createRewriter 幂等`、`关掉之后还原成宿主原文`。

### G15. 测试写到了真实用户目录
- **现象**：跑一次 `cargo test`，`~/.pi/agent/extensions/` 里多出文件，`~/.codex/config.toml` 被改。
- **原因**：`apply` 会解析**宿主主目录**，而那条路径来自真实环境变量与用户主目录 ——
  只注入 `METIS_HOME` 是不够的。
- **规则**：`Paths` 必须提供 `with_harness_root(...)`，把**所有**宿主主目录重定向到临时目录。
  任何会 `apply` 的测试都要用它。对应测试：`harness_root_override_redirects_every_harness`、
  `slash_channel_writes_host_products_into_the_isolated_home`（后者显式断言路径里含 `harness-homes`）。

### G16. 门禁自己把测试代码当成违规
- **现象**：`cargo xtask layers` 报 `slash.rs 直接起外部进程`，但那行在 `#[cfg(test)]` 里。
- **原因**：检查按整份文件做字符串包含，没区分测试代码。
- **规则**：静态检查要**跳过 `#[cfg(test)]` 之后的部分**（用 `text.split("#[cfg(test)]").next()`）。
  测试里调 node/cargo 是正当的。同时 `secrets` 检查要允许明显的假路径，
  但**注释里的示例路径也算泄漏**——改成 `~/.metis` 这种不含用户名占位的写法。

### G17. "一个文件"的落点模型装不下"每个 profile 一份"
- **现象**：DSH 的 install 通道报 `拒绝访问 (os error 5)` —— 它把 `profiles` 这个**目录**
  当成文件去写。改成目录展开之后，又把 `profiles/node_modules` 当成了一个 profile，
  插件被写进 `profiles/node_modules/metis/`。
- **原因**：`PersistTarget` 只有"相对路径 + 层级 + 写入方式"，没有表达"目录展开"的能力。
- **规则**：落点要能表达三种形状：**单文件**、**目录展开**（每个子目录一份）、**字段**。
  - 目录展开时必须用**可判定的特征**识别子目录（DSH 用 `package.json` 存在），
    不能只判断"是不是目录"；
  - 展开出来的产物必须放在宿主期望的**包路径**下（DSH 是 `node_modules/<name>/`，
    放 profile 根目录宿主找不到）；
  - 撤销要走**写它的那条路**（`slash::revert`），走 `revert_block` 一个文件都删不掉。

### G18. "内容一致就跳过"导致账本漏记
- **现象**：第二次 `apply` 之后 `disarm` 删不掉文件，留下孤儿。
- **原因**：安装逻辑写成"内容相同就不写"，于是那条路径**没有被记进账本**；
  撤销按账本走，就找不到它。
- **规则**：**写盘可以跳过，记账不能跳过**。内容一致时仍要 `record_owned`，
  否则"我写过什么"这件事会丢。对应测试：`install_is_idempotent` 要同时断言账本条数。

### G19. 撤销只删文件，不删自己建的空目录
- **现象**：`disarm` 之后文件没了，但 `<profile>/node_modules/metis/` 这个空目录还在。
- **原因**：撤销只处理账本里的文件条目。
- **规则**：撤销时把父目录也收集起来，**只删空的**（`remove_dir` 失败就忽略——用户往里
  放过别的东西是正常的）。对应测试：`disarm_removes_per_profile_products`。

### G20. 把插件放进目录 ≠ 宿主会加载它
- **现象**：DSH 的插件文件齐了、`node --check` 也过了，宿主就是不生效。
- **原因**：cordis 只在 `cordis.patch.yml` 里被 `- insert:` 点名的插件才会加载。
- **规则**：安装"需要声明才能生效"的产物时，**声明和产物必须成对做**（装时挂、卸时先摘）。
  顺序也有讲究：**卸载要先摘声明再删文件**，否则宿主会去找一个已经不存在的插件。

### G21. 逐字节还原：多加的换行必须被精确配对地切掉
- **现象**：挂载块插入时为了可读性多留了一个空行，撤销后文件多一个 `\n`，逐字节比对失败。
- **原因**：插入和切除的边界不对称。
- **规则**：任何"插入一段带边界标记的内容"的操作，插入与切除必须是**严格互逆**的：
  插入加的每个字节，切除都要按同样的规则拿回来。有测试
  `strip_removes_only_our_block`、`mount_then_unmount_round_trips_on_disk` 钉住。

### G22. YAML 文档根的 `[]` 后面不能直接接列表项
- **现象**：挂上 `- insert:` 之后宿主报 `end of the stream or a document separator is expected`。
- **原因**：宿主初始模板是空 flow 数组 `[]`；`[]` 是完整的文档节点，后面再接列表项就是非法 YAML。
- **规则**：写进宿主配置前先**归一化文档根**（把单独的 `[]` 摊平掉），但只处理**文档根那一行**：
  缩进里的 `[]` 和用户手写的 flow 数组原样保留。测试里用真实 YAML 解析器验证，而不是字符串断言。

### G23. 探测直接读真实 PATH，测试永远不可能稳定
- **现象**：`detect::tests::not_installed_when_neither_binary_nor_home_exists` 在开发机上失败 ——
  因为那台机器真的装着 `codex`。
- **原因**：探测函数内部直接调 `find_program`，没有接缝。
- **规则**：**凡是要读真实环境的函数，都要留一个可注入的版本**（`detect_with(find)`）。
  测试用 `|_| None` 把所有"外部世界"关掉，才谈得上确定性。

### G24. "配置目录存在" 推不出 "只有桌面版"
- **现象**：`doctor` 把 `pi`、`omp`、`opencode` 全报成"只有桌面版（无命令行入口）"，
  但它们明明有 CLI，只是那台机器没装。
- **原因**：`summary()` 用 `binary.is_none() && home_exists` 去推断"桌面版"。
  文件系统的状态**不能**推出产品的静态属性。
- **规则**：**静态事实只从静态表读**（`spec.probe.desktop_only`），文件系统只回答"目录在不在"。
  "装了但命令不在 PATH" 和 "没有命令行入口" 是两条不同的提示，各有各的下一步。
  对应测试：`config_dir_without_binary_is_not_reported_as_desktop_only`。

### G25. 脱敏只做了"预览字符串"，结构化输出照样泄漏
- **现象**：`metis launch omp --json` 的 `command` 字段是脱敏的，`args` 数组里却是完整人设 ——
  而脚本最常打印的就是 JSON。
- **原因**：脱敏写在了格式化函数里，只覆盖了那条路径。
- **规则**：**脱敏要做在数据层，不是展示层**。凡是可能带人设正文的字段（`args`、`command`、
  日志、错误详情）都要过同一个 `redact()`。对应测试：`launch_never_leaks_the_persona_body`。

### G26. XDG 风格的环境变量是"配置根"，不是宿主目录
- **现象**：`XDG_CONFIG_HOME=~/.config` 时，opencode 的产物被写到 `~/.config/plugins/`，
  正确位置是 `~/.config/opencode/plugins/`。
- **原因**：把所有环境变量都当成"就是宿主目录"。
- **规则**：环境变量有两种语义：**宿主目录型**（`CODEX_HOME`）与**配置根型**（XDG 风格）。
  表里用 `env_is_parent` 区分，两边各有回归测试。把这两种混为一谈，文件会写到完全无关的位置。

### G27. 截图"全白"不等于界面没渲染
- **现象**：GUI 开窗成功（`MainWindowTitle = Metis`），但 `CopyFromScreen` 截出来是全白，
  一度以为渲染坏了。
- **原因**：这台机器有虚拟显示适配器，且**整屏截图本身也是全白**（连记事本窗口都截不到内容）。
  这是抓屏机制的问题，不是界面问题。
- **规则**：GUI 渲染问题要用**能证明渲染的**手段验证：
  1. 先做对照实验（截一个已知窗口，比如记事本）—— 如果对照也白，就是抓屏坏了；
  2. 用 `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT=2)` 抓窗口自身，它会向窗口要一份渲染结果，
     不走桌面合成；
  3. 截图字节数是个便宜信号：全白 ~5 KB，真正有内容 ~150 KB。

### G28. egui 自带字体不含 CJK —— 中文界面会变成一堆方框
- **现象**：界面所有中文都是 `□ □ □`，按钮、标签、说明全不可读。
- **原因**：`egui` 的默认 `FontDefinitions` 只有拉丁字形；中文没有回退字体。
- **规则**：**中文产品必须在启动时加载系统 CJK 字体**（`msyh.ttc` / `PingFang.ttc` /
  `NotoSansCJK`），并把它加到 `Proportional` **与** `Monospace` 两个族的末尾
  （拉丁字符仍用 egui 自带字形，中文才回退）。找不到字体要**静默降级**，不能崩。
  有测试 `cjk_font_is_installed_on_this_machine` 守住这条。

### G29. "问这家整体在不在注入" 与 "问某条通道能不能用" 是两个问题
- **现象**：`codex` 已武装 `install`，界面上开关是亮的，状态行却说"没有已开启的通道"。
- **原因**：`harness.list` 用空上下文调 `resolve_activation`，而许可来源的判定要求
  `ctx.channel` 精确匹配某条通道 —— 空上下文永远匹配不上。
- **规则**：激活解析要区分两种问法：
  - `ctx.channel = Some(c)`：单通道判定（apply、doctor 用），语义不变；
  - `ctx.channel = None`：**聚合判定**（界面的状态行、`harness.list` 用），
    任意一条已武装的注入通道都算许可。
  但 `slash` 例外：它只是开关，光武装不构成注入。三条都有测试
  （`without_a_channel_context_any_armed_channel_counts` /
  `aggregate_slash_registration_alone_is_not_enough`）。

### G30. 筛选器不能把"没探测出结果"当成"确定没装"
- **现象**：取消勾选「显示本机没装的」之后，整张列表空了 —— 因为探测没跑、
  `installed` 全是 `None`。
- **原因**：`filter(|row| row.installed.unwrap_or(false))`。
- **规则**：**未知要保留**。`None`（还没探测）与 `Some(false)`（确认没装）是两回事；
  把未知藏掉会让用户以为这家不存在。用 `unwrap_or(true)`，并有测试
  `installed_only_filter_keeps_unknown_rows_visible`。

### G31. 杀进程只杀到直接子进程 → 读管道的线程永久阻塞
- **现象**：`metis verify codex` 挂死好几分钟不返回；设了 3 秒墙钟却完全无效。
- **原因**：`child.kill()` 只杀直接子进程。它的子进程（node 等）还活着并**攥着
  stdout 管道**，所以排空线程永远读不到 EOF，`join()` 就永远等下去。
  墙钟只覆盖了 `try_wait` 循环，没覆盖"等待输出线程"这一步。
- **规则**：外部进程必须**两级防护**：
  1. 用作业对象（Windows）/ 进程组（Unix）杀**整组** —— `process-wrap` 的
     `JobObject` / `ProcessGroup`；
  2. 等待输出线程也要**有界**（`join_bounded`）。拿不到数据就放弃，"不挂死"优先于
     "拿到全部输出"。
  对应测试：`timeout_does_not_hang_on_a_child_that_holds_the_pipe`（硬断言 10 秒内返回）。

### G32. 验证工具的"隔离"必须由调用方持有 provider
- **现象**：端到端测试里宿主连不上假 provider，永远报 `no-request`。
- **原因**：`verify_one` 内部自己起 provider，调用方拿到的 `base_url` 是**另一个**
  实例的端口 —— 配方指过去当然连不上。
- **规则**：需要**先知道端口才能配参数**的流程，provider 的生命周期必须交给调用方。
  拆成 `verify_with(input, &provider, …)` + `verify_one`（自己起一个再转调）。
  对应测试：`verify_detects_a_developer_layer_hit_end_to_end`。

### G33. `Mutex` 在测试夹具里是合理的，但要有理由
- **现象**：`clippy` 拦住 provider 里的 `std::sync::Mutex`。铁律 10 说不要用裸 Mutex。
- **原因**：铁律 10 针对的是**跨进程/跨模块的锁契约**；provider 里的 Mutex 只保护
  测试夹具内部两小块状态（抓到的请求、当前标记），不参与任何锁序。
- **规则**：确实是这个唯一合理用途时，**在模块顶部显式豁免并写清理由**
  （`#![allow(clippy::disallowed_types)]` + 一行说明），而不是改铁律或偷偷 `#[allow]`。

### G34. 只读导入也要证明"源目录一个字节都没变"
- **现象**：`import` 的测试一开始只断言"目标导入成功了"，没断言源目录。
- **原因**：一个"只读"的承诺，只要没测试就随时可能被一次顺手 `fs::write` 破坏。
- **规则**：任何标称"只读源"的功能，都要有一条测试**在导入前后比对源文件字节**。
  对应测试：`source_directory_is_never_modified`。同理，"dry-run 不动磁盘"也要
  同时断言文件与账本都没变（`dry_run_touches_nothing`）。

### G35. "有残留就保留数据目录"必须显式测
- **现象**：`self-uninstall` 里"有失败项时保留数据目录"这条分支，如果只测成功路径就永远不知道它对不对。
- **原因**：失败路径最容易写成"尽力删除"，而那正是会毁掉用户恢复材料的行为。
- **规则**：破坏性操作的**每条失败分支**都要有一条测试：
  构造一个注定失败的账本条目（比如指向损坏的 JSON），断言数据目录**还在**、
  `leftovers` 里列出了具体路径。对应测试：`everything_scope_keeps_the_dir_when_something_failed`。

### G36. 导入时"不导入 armed"是有意的，不是漏了
- **现象**：从上游导入后，人设和默认执行器都在，但"接管"状态是空的，看起来像导入不完整。
- **原因**：两边的托管块标记不同（`agent-purge` vs `metis`），把 `armed` 直接搬过来会
  指向已经不存在的落点。
- **规则**：**状态里凡是"指向某个落点"的字段（`armed`、`projectDirs`），跨实现迁移时一律不导入**，
  并要求用户重新 `arm` 一次。报告里要明写这条，否则用户会以为坏了。

### G37. `Panel::top` 里的"右对齐按钮组"会静默消失，而所有测试都是绿的
- **现象**：真机截图上顶栏只剩"就绪"两个字，`实测验证 / 应用变更 / 刷新状态` 三个按钮
  完全不见；但无头渲染测试全绿。
- **原因**：试了三种写法都不行，值得记下来：
  1. `ui.horizontal` + `with_layout(right_to_left)` —— 子布局拿到的可用宽度是 **0**；
  2. `allocate_ui_with_layout(vec2(ui.available_width(), h), …)` —— `Panel::top` 的默认高度
     是 `None`（按内容撑开），协商阶段 `available_width()` 也是 0，整条顶栏塌成空行；
  3. `ui.max_rect()` —— 同样是协商前的值，不可靠。
- **规则**：`Panel::top` 里**先画控件、让面板按内容撑高**，不要依赖任何"剩余宽度"计算。
  用普通 `left_to_right` 把需要的东西一次画完；确实要右对齐时，用 `ui.with_layout` 之前
  必须先有确定的宽度（例如外层给它一个 `min_width`）。
  **回归测试要断言"画了多少图元 / 内容有多高"**，而不是只断言"没 panic" ——
  控件被挤出去时不会 panic。对应测试：`topbar_renders_every_action_it_offers`。

### G38. 测试"全绿"也可能没覆盖到你正在改的那条路径
- **现象**：顶栏按钮消失了两轮，`cargo test` 一直是绿的。
- **原因**：无头渲染测试只断言"不 panic"，而控件被挤出可视区**不会 panic**。
- **规则**：UI 的"显示出来了"必须用**可量化的证据**断言：图元数量、内容包围盒高度、
  或者截图字节数（全白约 5 KB，有内容 150 KB 以上）。只断言 `is_ok()` / 不 panic 的
  UI 测试等于没测。

### G39. 版本号不能按字符串比
- **现象**：`update` 用字符串比较版本，`"0.10.0" < "0.9.0"`，已经是最新的用户被反复提示升级。
- **原因**：字典序与语义版本序不同。
- **规则**：解析成 `(major, minor, patch, pre)` 再比，并且**明确预发布规则**：
  核心相同时 `rc → 正式版` 算升级，`正式版 → rc` **不算**（不把稳定用户拽到预览版）。
  对应测试：`numeric_comparison_beats_string_comparison`、`stability_rules`。

### G40. 日志裁剪时"记录自己"会凭空多出一个月份文件
- **现象**：`prune` 删到只剩 1 个月，结果磁盘上还是有 2 个 —— 因为裁剪动作本身写进了"当月"，
  而当月正好是被删掉的那个，于是又新建出来。
- **原因**：先删、再按"现在"追加。
- **规则**：**先决定留哪些，再把记录写进"保留下来的最新月份"**，不要用"当前时间"去选文件。
  对应测试：`prune_keeps_the_newest_months`、`prune_records_itself`。

### G41. "查不到"不等于"已是最新"
- **现象**：仓库还没有公开 Release 时，`update` 报 `available: false`，用户以为已经是最新版。
- **原因**：把 `404`（没有发布）和"确实没有新版本"混成一个结果。
- **规则**：`available: false` 必须再分两种情况：`error` 有值 = **查不了**；
  `error` 为空 = **查过了，确实没有更新**。界面上这两种文案必须不同。
  对应测试：`missing_release_is_reported_as_not_checkable`。

### G42. 网络与文件系统都要有注入点
- **现象**：`update` 的核心逻辑一开始直接调 `ureq`，测试要么真联网、要么干脆不测。
- **原因**：把网络调用写死在业务函数里。
- **规则**：`check(options, fetch)` 这种形状 —— **网络是可注入的闭包**，测试传假响应；
  生产才传真的 `ureq`。同理，凡是"读外部世界"的函数都要能注入（探测、时钟、网络）。
  这已经在 `detect_with`（G23）和 `verify_with`（G32）上重复过三次，是同一类问题的第三次。

### G43. `owner/repo` 里 `..` 是合法字符，但会造成路径穿越
- **现象**：`parse_repo("../x")` 通过了校验，因为 `.` 在允许的字符集里。
- **原因**：只做了字符集白名单，没做"这个值本身是不是路径片段"的判断。
- **规则**：凡是会被拼进 URL / 路径的用户输入，除了字符白名单，还要显式拒绝
  `.`、`..`、以及以 `.` 开头的值。对应的测试要**真的写 `../x` 这种输入**，
  而不是只测"含空格/含斜杠"。对应测试：`parse_repo_rejects_junk`。

### G44. 导入"成功"可能是假成功：同名同内容也报 imported
- **现象**：同一份人设导入两次，两次都报 `imported`，用户以为又写了一遍。
- **原因**：只判断"目标在不在"，没判断"内容是不是一样"。
- **规则**：导入的结局要分四态：`imported` / `overwritten` / `identical` / `skipped` / `failed`。
  **内容相同必须报 `identical`**，否则报告在说谎（"写入了"但实际什么都没变）。
  对应测试：`import_dir_is_idempotent_and_reports_identical`。

### G45. 布局验证不能只看"渲染出来了"
- **现象**：`M6.12` 一度只做了"开窗 + 截图确认能渲染"，就以为布局没问题。
- **原因**：截图能证明"有内容"，但证明不了"最小窗口下不被裁"。
- **规则**：布局验证要在**每个目标尺寸**下单独截一次，并明确检查：横向无溢出、
  关键标签完整可见、长列表可滚动。尺寸至少覆盖最小窗（`900×620`）与默认窗。
  高 DPI 要单独验（`150%` / `200%`），不能靠"1080p 下看着对"推断。

### G46. "每个错误都有补救建议"这条规则，靠人记就是没有
- **现象**：`AGENTS.md` 从第一天就写着"任何面向用户的失败都要有补救建议"，
  但代码里积累了 **19 处**没写的。没人发现，因为没有任何机制检查它。
- **原因**：规则只写在文档里，没有被自动化。
- **规则**：**能被机器检查的规则必须机器化**。做成了 `cargo xtask remediation`：
  源码扫描每个 `MetisError::new(...)`，看调用链里有没有 `with_remediation`；
  `Internal` 类豁免（程序缺陷，用户无事可做）。
  而且检查本身要有测试（`the_real_workspace_is_clean` 扫真实仓库）。
  这是 `PITFALLS.md` F2 那条"规则要么能被机器检查，要么不存在"的又一次实例。

### G47. 补上 remediation 会让"断言 remediation 为 null"的测试变红
- **现象**：给 `core` 的一条错误补了补救建议后，`json_shape_is_stable` 失败 ——
  它断言 `remediation` 是 `null`。
- **原因**：测试原本用"一个真实的错误"去验证"没有补救建议时 JSON 长什么样"，
  而那个错误现在有补救建议了。
- **规则**：测试**用一个明确没有 remediation 的构造**去验证"空"的分支
  （例如 `ErrorKind::Internal`），而不是依赖"某个业务错误恰好没有"。前者不会因为
  业务变化而失效。

### G48. 一条从未跑通过的门禁，和没有门禁是一回事
- **现象**：`cargo xtask coverage` 里写着 `--fail-under-branches 80`，而这个参数
  **在 `cargo llvm-cov` 里根本不存在**（只有 `--fail-under-lines` / `-functions` /
  `-regions` / `-file-lines`）。也就是说这条门禁从项目第一天起就没成功跑过一次，
  但它在文档里、在"完成前检查"清单里都「看起来存在」。
- **原因**：写门禁时凭印象加参数，写完没有真跑一遍。
- **规则**：**新增或修改门禁的第一步是把它跑一次，确认它会退出 0**。
  门禁的价值在于"它真的会失败"，而不是"它出现在文档里"。
  对做不到自动化的指标（比如分支覆盖率），在文档里写明"人工检查"，不要假装自动。
  核实方式：`<tool> --help | grep fail-under`。

### G49. 测试里"真实联网"是偶发失败的常客，也是纪律违规
- **现象**：`github_import_is_reachable_and_fails_cleanly_offline` 真的去请求
  `api.github.com`。平时 0.3 秒就失败并通过；但并发跑覆盖率时它偶发让整个
  `cargo llvm-cov` 以 101 退出，看起来像"覆盖率不达标"。
- **原因**：把"路由到网络导入器"这件事，用一个真实网络请求去验证。
- **规则**：测试**不得访问外网**（`AGENTS.md` 测试纪律）。验证"路由"要注入，
  或者只测"坏输入在发请求之前就被拒"。判断方法很简单：**一条单元测试如果耗时
  跟网络有关（0.3 秒 vs 0.02 秒），它就在联网**。

### G50. 提高覆盖率最省力的顺序：先修"有逻辑但零测试"的文件
- **现象**：总覆盖率卡在 87.7% 上不去。真正拖后腿的不是"难测的 GUI 绘制"，
  而是 `apps/metis-gui/src/main.rs`（**0%**，从来没测过）和 `harness/src/spec.rs`（**40%**，
  完全没有测试模块）。
- **规则**：提覆盖率按这个顺序找目标：① 覆盖率极低且**含真实逻辑**的文件（启动守卫、
  参数解析、纯判定函数）；② 有大量分支但只测了主路径的模块；③ 纯绘制代码（最后做，
  收益最低）。先补①，往往一两个文件就能顶几个百分点。

### G51. "读写都有实现"不等于"读写被接上了"
- **现象**：`UiState::load` / `UiState::save` 都写好了、都有测试，但深色主题、
  侧栏宽度、"记住上次的屏幕"——**全都不生效**。真机上两张截图（浅色 / 深色）的
  MD5 完全相同。
- **原因**：`MetisApp::new` 用的是 `UiState::default()`，从没人调用 `UiState::load`。
  `App::save` 那一侧是通的（会写），读那一侧**根本没接线**。
- **规则**：持久化功能要有一条**端到端**测试：「写入 → 重建对象 → 读出」。
  只测 `load()` 和 `save()` 各自正确，测不出"中间没接线"。
  另外：**截图 MD5 相同是很强的信号** —— 改了视觉相关代码后截图字节数一模一样，
  基本就是"改动没生效"，而不是"改得看不出来"。

### G52. 手抄的清单会和真实注册表脱节
- **现象**：给 I9 一致性测试手写了一份"CLI 命令 id 清单"，结果里面有
  `status.show` / `config.revert` / `persona.delete` 三个**不存在的** id
  （真实的是 `state.status` / 没有 config.revert / `persona.remove`）。
- **原因**：凭记忆和命名习惯写清单，而不是从注册表取。
- **规则**：**清单类断言必须从"唯一真相来源"取值**。真需要写死一份时，
  先打印真实注册表再抄（`cargo test -- --nocapture` 打一遍 `commands.ids()`），
  并让测试在有新命令时失败提醒你更新它。这次正是测试自己抓到了三个错 id。

### G53. 并行化之后要钉住"顺序不变"
- **现象**：`detect_all` 改成并行后，如果直接用完成顺序收集结果，
  15 家的顺序每次刷新都会变，界面上列表会跳。
- **规则**：并行化**只能改耗时，不能改可观察的顺序**。做法是
  `ids.zip(join 结果)` —— 结果按下标归位，而不是按完成时间。
  并且要有一条测试专门钉住顺序（`parallel_detection_keeps_the_registry_order`）。

### G54. `include_str!` 的资源，没人用就会被优化掉
- **现象**：两张 i18n 表用 `include_str!` 编译进来，`translate()` 也有测试。
  但在 `metis.exe` 里**搜不到**表里的任何字符串（逐字节搜索确认）。
- **原因**：没有任何生产代码调用 `translate`，只被测试调用 —— 全程序优化把整张表删了。
  二进制里没有表，而所有测试都是绿的。
- **规则**：**`include_str!` 的资源必须有生产路径真正读取它**。加了资源之后，
  除了单元测试，还要有一条**从二进制层面**验证它真的进去了（或者至少有一个 CLI 子命令
  会读它）。查法：`Select-String -Path <exe> -Pattern '<表里的字符串>'`
  或逐字节搜索 —— 这个检查比"测试通过"可靠得多。

### G55. 依赖墙钟的测试会在覆盖率环境下偶发失败
- **现象**：`parallel_detection_is_faster_than_serial` 平时一直通过，
  但 `cargo xtask coverage` 偶尔以 101 退出（并行跑 15 家 + 插桩，机器负载高，
  并行就不比串行快了）。看起来像"覆盖率不达标"，实际是一条计时断言。
- **原因**：我自己在 `AGENTS.md` 里写着"不写依赖墙钟的测试"，然后写了这么一条。
- **规则**：并行化的测试要断言**结果一致**，不是**速度更快**。
  速度是副作用，不是契约；把它写进断言就是把机器负载变成测试结果。
  验证速度要在真机上手工比（`time metis doctor`），不要进 CI。

### G56. 加了一个 `unreachable!` 就是给自己埋一颗雷
- **现象**：给 `translate` 加分支时用了 `unreachable!("i18n 在 translate 之前已处理")`，
  clippy 立刻拦住（本项目 `deny(unreachable)`）。
- **规则**：铁律 1 禁止 `unreachable!`，即使逻辑上真的到不了。改成返回
  `ErrorKind::Internal` + 补救建议 —— 万一将来有人调整顺序，用户看到的是一条可诊断的错误，
  而不是"程序已停止工作"。

### G57. 单线程 accept 会被一个"连上但不发数据"的客户端卡死
- **现象**：假 provider 用单线程 `accept` → `handle` 串行处理。用 `curl` 连打 30 次，
  26 次成功、4 次返回 `000`（连接失败）；node 侧表现为 `TypeError: fetch failed`。
- **原因**：`handle` 里 `read_line` 是阻塞的（超时 5 秒）。任何一个连接在"已建立但尚未发数据"
  的窗口里，整个 accept 循环就被占住，后续连接全部超时——**包括本该成功的那些**。
- **规则**：**测试用的假服务端也必须每连接一个线程**。单线程串行只适合"确定一次只有一个客户端"的场景；
  探测、重试、连接池都会打破这个假设。改完之后 node 连打 30 次 30 成功。

### G58. 端到端测试里放真实网络栈，就是给自己制造偶发
- **现象**：`verify` 的两条端到端测试起真实 `node` 进程 + 真实 TCP，在并发和插桩构建下
  约 30% 概率失败（宿主输出是 `fetch failed`，但 provider 本身正常、node 退出码 0）。
  试过：加互斥锁、加大收尾窗口、加就绪探测——**全都不能根治**（就绪探测反而把失败率推到 80%，
  因为它与真实请求抢 accept）。
- **原因**：测试里同时存在两个非确定因素——外部进程调度 + TCP 栈时序。它们的组合不受测试控制。
- **规则**：**端到端测试的"端"越少越可靠**。正确做法不是调参数，而是**换掉不确定的那一端**：
  用进程内 TCP 客户端扮演宿主（`in_process_host`），只保留"provider → 抓请求 → 判层"这条链路，
  把"用 `Exec` 起外部进程"交给 `metis-process` 的单元测试单独覆盖。
  真实 `node` 的那两条用 `#[ignore]` 保留，`docs/TESTING.md` 里登记替代关系。

### G59. 判层逻辑要能被"不联网"地测
- **现象**：一开始只有 `node` 端到端测试覆盖"人设落在 developer / user / system 层"的判定。
- **规则**：判定逻辑（`extract_roles` + `hit_role`）必须有**纯函数级**的单元测试，
  端到端只是补充。这样即使端到端被标记为 `ignore`，覆盖率与信心都不掉。
  对应测试：`captures_a_system_message` / `captures_a_developer_role` /
  `a_developer_message_is_judged_ok_end_to_end`（进程内）。

### G60. 同一个错误我犯了三次：`for _ in 0..200 { sleep }`
- **现象**：`app::tests::spawn_refresh_eventually_fills_the_snapshot` 用
  "循环 200 次 × sleep 10ms" 等后台任务；`busy_flag_tracks_jobs` 用"5 秒上限"。
  两者在机器忙的时候都偶发失败 —— 而 `AGENTS.md` 的测试纪律**明确写着**
  "不写依赖墙钟的测试"。
- **原因**：把"防止死锁的上限"当成了"正常路径的预算"。200×10ms = 2 秒，
  在并发跑全量测试时根本不够。
- **规则**：等待异步完成只有一种正确写法：
  ```rust
  while still_busy() {
      poll();
      if Instant::now() >= deadline { break }  // 只防死锁
      sleep(SHORT);
  }
  ```
  上限设成 **30 秒**（正常路径永远第一个条件就退出，所以不影响速度），
  并且**全局只有一个 `wait_for_idle` 辅助函数**，不要在每处手抄一遍。
  同一个仓库里出现三种不同的等待写法，就说明这条规则没被执行。

### G61. 覆盖率门禁会因并发抖动偶发失败，要用"连跑三次"确认
- **现象**：`cargo xtask coverage` 时好时坏，退出码在 0/1 之间跳。
- **原因**：它内部要跑一遍完整测试；只要有一条偶发失败，整个门禁就红 ——
  看起来像"覆盖率不达标"，实际是别的问题。
- **规则**：覆盖率门禁红了，**先看是不是有测试失败**，再怀疑覆盖率。
  排查方式：`cargo llvm-cov --workspace --no-report` 单独跑一遍看 `FAILED`。
  确认修好之后要**连跑三次**才敢说"稳定"（一次通过可能是运气）。

### G62. 字符串 `Replace` 静默失败，功能就"看起来失灵"
- **现象**：命令面板做完了、`Ctrl+K` 也绑了、顶栏按钮也画了，
  但**点它完全没反应**。用 `agent-desktop` 抓语义树才看到：
  按钮在、能点、`palette.open` 也置上了 —— 但**没有任何地方去画面板**。
- **原因**：把"在主循环里调用 `palette::show`"这一步用字符串 `Replace` 插进去，
  而当时那段代码已经被 `cargo fmt` 改过格式，`Replace` 没匹配上，
  **静默什么都没做**。Rust 编译器当然不会报错——它根本不知道有这回事。
- **规则**：**结构性改动（新增一个调用点、新增一个模块注册）不要用字符串替换**。
  用 `edit` 工具（它会校验原文存在且唯一），或者替换完立刻 `grep` 确认。
  这类"以为改了其实没改"的 bug 编译器抓不到，测试也可能抓不到
  （因为缺的是一个调用，不是逻辑错误）—— 只能靠**真机点一次**。

### G63. 快捷键被"有焦点就让路"的守卫挡死
- **现象**：`Ctrl+K` 打不开命令面板；而且**点过任何按钮之后**它永久失效。
- **原因**：`handle_shortcuts` 开头有 `if ctx.memory(|m| m.focused().is_some()) { return }`，
  用来防止"在搜索框里打 r 触发刷新"。但界面里**任何时候都有控件持有焦点**，
  于是这条守卫把所有快捷键都废了。
- **规则**：区分两类快捷键：
  - **全局唤起型**（`Ctrl+K` 命令面板）：**不受焦点限制**，它本来就是"从任何地方打开"；
  - **操作型**（`Ctrl+R` 刷新、`Alt+1..4` 切屏）：有焦点时让路。
  把全局唤起型放在焦点检查**之前**。对应测试：
  `ctrl_k_opens_the_palette_even_while_a_widget_has_focus`。

### G64. `wait_for(1)` 用在"起了两个任务"的测试里，必然等满超时
- **现象**：`metis-ui-egui` 的测试套件固定耗时 **30.0 秒**（和某个超时值一模一样）。
  所有测试都是绿的，所以没人多想。
- **原因**：`wait_for` 收到**第一个**非空结果就返回。某个测试起了 2 个 job 却分两次等，
  第二次时两个都已被消费完，于是循环跑满 30 秒才退出。
  我上一轮为了"防死锁"把超时从 5 秒提到 30 秒，正好把这个 bug 放大了 6 倍。
- **规则**：等待异步完成要**显式声明期望几个结果**（`wait_for_n(jobs, 2, …)`），
  不要用"等到非空"。另外：**测试套件耗时恰好等于某个超时值，就是个信号**——
  正常路径几乎不会恰好卡在整数值上。

### G65. 瞬时 UI 状态被持久化 → "启动就弹窗、而且关不掉"
- **现象**：GUI 一启动命令面板就自己打开；按 Esc 关了之后，下次启动又回来。
  用户的原话是"没法关闭"。
- **原因**：`PaletteState` 被 `serde` 序列化进了 eframe 的 storage。
  上次退出时面板开着 → `open: true` 落盘 → 下次启动读回来就弹出；
  关掉后如果又存了一次 `true`（或没存到），表现就像"关不掉"。
- **规则**：**"正在输入 / 正在打开"这类瞬时状态绝不持久化**。
  判断标准：它跨进程保留有意义吗？面板开没开、搜索词是什么、弹窗在不在 —— 都没有。
  该持久化的是**偏好**（主题、侧栏宽度、上次看的屏幕）。
  对应测试：`the_command_palette_is_never_persisted`、
  `a_persisted_state_reopens_with_a_closed_palette`。

### G66. 焦点守卫会吃掉"全局唤起型"快捷键
- **现象**：命令面板的 `Esc` 关不掉 —— 输入框聚焦时，egui 把 `Esc` 解释成
  "取消编辑"并消费掉，面板里 `consume_key` / `key_pressed` 都收不到。
- **原因**：把 `Esc` 放在**面板内部**处理，而面板自己就是那个持有焦点的输入框的宿主。
- **规则**：**全局唤起/退出型快捷键（`Ctrl+K`、`Esc`）必须在应用层、
  焦点守卫之前处理**，用 `ctx.input(|i| i.key_pressed(..))`（只看"有没有按下"，
  不管谁消费了它）。操作型快捷键（`Ctrl+R`、`Alt+1..4`）才应该在有焦点时让路。
  这条和 G63 是同一个根因的两次表现。

### G72. `serde(skip)` 的字段反序列化后是 `Default::default()`，不是结构体的默认值
- **现象**：`import_source` 在 `UiState::default()` 里设成了官方源，但真机启动后
  输入框显示的是**占位符 `owner/repo`**（空的），用户会以为"默认没填"。
- **原因**：`#[serde(skip)]` 在**反序列化**时给的是 `String::default()`（空串），
  而不是整个结构体 `Default` 里的那个值。`UiState::load` 只有在"没有存过"时
  才走 `Self::default()`；存过之后走 `from_str`，skip 字段就是空的。
- **规则**：`serde(skip)` 的字段如果**需要非空默认值**，必须在 `load` 之后**补一次**。
  对应测试：`the_import_source_defaults_to_the_official_repo`。

### G73. `horizontal` 里用 `available_width()` 减常数算宽度，按钮会被挤出去
- **现象**：导入卡片里"输入框 + 预览 + 导入"排一行，真机截图里**两个按钮不见了**
  （被挤出卡片右边界外）。
- **原因**：在 `ui.horizontal(|ui| ...)` 里，`ui.available_width()` 会**随前一个控件
  放下去而缩小**；用"当前可用宽度 − 210"算输入框宽度，算出来的值和后面按钮实际
  需要的宽度对不上，按钮就被推到可视区之外。
- **规则**：`horizontal` 里**不要用"可用宽度减常数"来分配**。要么让输入框独占一行
  （`desired_width(f32::INFINITY)`），要么用 `ui.with_layout(right_to_left)` 把按钮
  钉在一侧。判断方式是**看截图**：控件数不对就是布局问题，不是渲染问题。

### G71. mock 测试全绿，真实 GitHub 一次都没通过
- **现象**：`import owner/repo` 的单元测试一直绿，但真连一次 GitHub 全挂。
  前后暴露出三个问题：字段名写成 `kind`（GitHub 返回 `type`）、
  `raw.githubusercontent.com` 在这台机器**不可达**、逐份下载撞 API 限流。
- **原因**：mock 是**按我们自己的假设**造的 JSON。字段名错了，mock 里也跟着错，
  于是测试和实现一起错、一起绿。
- **规则**：凡是"对接外部协议"的代码（HTTP 字段、压缩包布局、命令行输出），
  **必须有一次真实调用的验证记录**写进 PR/文档；mock 测试只保证逻辑分支，
  不保证协议对不对。另外：换下载通道时要先**实测各域名的可达性**，
  不能假设"GitHub 的域名都通"。
- **本项目的具体结论**（2026-11-06 实测这台机器）：
  `github.com` ✅ / `api.github.com` ✅（限流 60/h）/ `codeload.github.com` ✅ /
  **`raw.githubusercontent.com` ❌ 不可达**。所以选 codeload tarball。

### G74. 测试里的 Windows 路径字面量，在 Unix 上是"相对路径"
- **现象**：CI 的 Linux 测试红了一片，报的却是些看起来无关的断言
  （`left: "D:\work/D:\data\metis"`、`gate_refuses_cwd_inside_home` 不拒绝）。
- **原因**：测试里写 `Path::new("C:\\Users\\example")`。反斜杠在 Linux/macOS 上
  **只是普通字符**，所以那一整串是**一个文件名**（相对路径）：
  没有 `parent()`、`components()` 拆不出层级、`starts_with()` 永远不成立。
  所有依赖路径语义的断言在 Unix 上全部失真。
- **规则**：测试里构造绝对路径**必须平台感知**，别写盘符字面量：
  ```rust
  fn abs(parts: &[&str]) -> PathBuf {
      let mut out = if cfg!(windows) { PathBuf::from("D:\\") } else { PathBuf::from("/") };
      for part in parts { out.push(part); }
      out
  }
  ```
  例外：**纯字符串比较**（比如 `owner_key` 的大小写归一）用字面量是安全的，
  因为它不解析路径结构。

### G75. `egui::Area` 第一帧只登记，不产出几何
- **现象**：无头渲染详情浮层，"选中后应有内容"的测试只数到 **8 个图元**
  （只有背景层），看起来像浮层根本没画。
- **原因**：`Area` 的尺寸/位置要到**第二帧**才定下来。只跑一帧看到的是
  "刚登记、还没排版"的中间态。而 `harness_detail` 单独调用（不用 Area）
  是能画出东西的 —— 这个差异一开始把我引向了错误的方向。
- **规则**：无头测 `Area` / 浮层类 UI，**至少跑 2~3 帧**再数图元。
  这也是为什么"同一块面板，同级渲染正常、放进浮层就消失"这种结论要警惕 ——
  先确认是**真的没画**，还是**只测了第一帧**。

### G69. `HarnessId::parse` 只校验格式，不校验"已注册"
- **现象**：`metis install nope` 一路"成功"，打印"已为 1 家开启 install 通道：nope"，
  实际什么都没写、也没报错。
- **原因**：`HarnessId::parse` 接受**任意合法字符串**（这是有意的——它允许用户自定义
  harness id）。用它做"用户输入校验"时，格式合法的拼写错误就被放过去了。
- **规则**：凡是"用户点名某一家"的入口，要校验两件事：
  ① 格式合法（`HarnessId::parse`）；② **在 `harness::registry::all()` 里存在**。
  报错用 `UnknownHarness` + 列出可用清单，退出码 2。
  对应测试：`install_rejects_an_unregistered_harness_with_code_2`。

### G70. 文档过时会让你自己汇报错的数字
- **现象**：`PARITY.md` 里 40+ 项标着"未做"，实际 90% 已实现。
  我一度照着它汇报"还缺这些"，差点误导维护者。
- **原因**：一直在更新 `ROADMAP` 和 `STATUS`，**漏了 `PARITY`** ——
  而按 `AGENTS.md` 它才是"唯一对齐基线"。
- **规则**：三份文档（`ROADMAP` / `STATUS` / `PARITY`）**每次完成功能都要一起回写**。
  核对方式：跑一遍真实 CLI（`--help` + 一次实际调用），**不要凭代码猜**。
  清点剩余工作时要**交叉核对三份**，任缺一份都会漏。

### G68. 手绘控件在无障碍树里"根本不存在"
- **现象**：用 `agent-desktop` 抓语义树，侧栏四个导航项里**只有一个**能被读到，
  而且 role 是 `statictext` 而不是按钮。对读屏用户来说，**整个侧栏是不存在的**。
- **原因**：`ui.allocate_exact_size()` + `ui.painter().text()` 画出来的控件
  **不会自动产出 accesskit 节点**。`egui` 只为它自己的 widget（`Button`/`Checkbox`…）
  登记语义；手绘的东西它不知道你在画什么。
- **规则**：**凡是手绘的可交互控件，都必须显式登记语义**：
  ```rust
  response.ctx.accesskit_node_builder(response.id, |node| {
      node.set_role(egui::accesskit::Role::Button);
      node.set_label(label);
      node.set_description(hint);
      node.set_selected(selected);
      node.add_action(egui::accesskit::Action::Click);
  });
  ```
  验证方式不是"代码写了"，而是**用 `agent-desktop` 抓一次语义树**看 role 与 name。
  这条也是"UI 自动化测试能跑起来"的前提 —— 控件在语义树里不可寻址，就没法点它。

### G67. 快照测试的前提是"渲染完全确定"，而它不会自动成立
- **现象**：快照基线刚生成，**下一次跑就对不上**。5 张全部抖动。
- **原因**：fixture 里有两个会变的东西：① 临时目录名每次不同，
  而状态栏会把 `state.json` 的完整路径画出来（差异集中在 `x[480..613] y[878..889]`）；
  ② `refresh_blocking` 留下的提示条文案可能不同。
- **规则**：做快照基线之前，**先证明渲染是确定的**：连跑两次比哈希，全部一致才开始用。
  要固定的东西包括：路径（用固定的假路径而不是 tempdir）、提示条、busy 状态、
  任何 `Instant::now()` 派生的内容。
  另外：**定位差异区域**（逐像素找出边界框）比盯着两张图看有效得多 ——
  坐标直接告诉你是哪一块在抖。

### G76. Windows 上 `curl` 报 `CRYPT_E_NO_REVOCATION_CHECK`，不代表服务端挂了
- **现象**：探测 `https://n.kkpt.tech:8443` 时 `curl` 直接 `000`，错误是
  `schannel: next InitializeSecurityContext failed: CRYPT_E_NO_REVOCATION_CHECK`，
  看起来像证书/网络故障。
- **原因**：Windows 的 schannel 在做证书吊销检查，而吊销服务器不可达；这与目标站点是否可用无关。
- **规则**：遇到这个错误先用 `curl --ssl-no-revoke` 或 `openssl s_client` 复核；
  两者能通就说明是**本机 TLS 栈**的问题，不是服务端。Rust 的 `ureq`/rustls 默认不做 OCSP，通常不受影响。
  对应实测：该站点证书由 Let's Encrypt 签发，`--ssl-no-revoke` 下列表/详情均 200。

### G77. Caddy 会按 `Accept-Encoding` 返回 zstd，ETag 也随之变
- **现象**：同一个 URL，协商到 zstd 时响应带 `content-encoding: zstd`，ETag 是
  `"<hash>-zstd"`；发 `accept-encoding: identity` 时是明文，ETag 是 `"<hash>"`。
- **原因**：Caddy 的压缩中间件按内容编码变体生成不同的 ETag；两者不是同一份响应的“同一个版本”。
- **规则**：**客户端固定发 `Accept-Encoding: identity`**，不做 zstd 解码，ETag 也因此稳定。
  如果中间代理仍然返回 `content-encoding: zstd`，明确报错而不是把它当 JSON 解析。
  对应测试：`unexpected_content_encoding_is_reported`、`conditional_request_uses_etag_and_304_returns_cache`。

### G78. worldd 的 Hub API 在 origin，不在 `/hub` 页面下
- **现象**：用户给的地址是 `https://n.kkpt.tech:8443/hub`；直接拼 `/hub/v1/hub/items` 会 404。
- **原因**：`/hub` 是网页（`text/html`），API 是 origin 的 `/v1/hub/*`。
- **规则**：输入归一化时把结尾的 `/hub` 去掉，只保留 scheme + host + port；
  其他 path 一律拒绝并给出示例。对应测试：`parse_hub_url_accepts_origin_and_hub_page`。

### G79. `nextCursor` 是 offset 且“满页就给”，不能当成“还有更多”
- **现象**：服务端的实现是 `items.len() == limit` 就返回 `nextCursor = offset + limit`；
  最后一页正好满时仍会给游标，再翻一页得到空列表。
- **原因**：把“这一页满了”误当成“后面还有”。
- **规则**：游标**不透明、不解析**；把空页当作终点，显示“没有更多了”并禁用下一页。
  offset 分页在两次请求之间有条目更新时会跨页重复/漏项，客户端按 `(kind, slug)` 去重。

### G80. 技能目录的归属只能靠 manifest 证明
- **现象**：如果“目录存在就覆盖/删除”，用户自己放在 `~/.metis/skills/<slug>/` 里的文件会被一起删掉。
- **原因**：路径存在 ≠ 这个目录归我们所有；远端 slug 也可能和用户手工建的目录撞名。
- **规则**：`.metis-hub.json` 是**唯一归属凭据**：更新/移除只处理它列出的文件；
  没有清单的目录**不覆盖、不删除**，安装要 `--overwrite`，移除只报告“没有清单”。
  目录里剩下的用户文件列进 `leftovers`，不能为了“清干净”把它们删掉。
  对应测试：`remove_deletes_only_managed_files_and_keeps_user_files`、
  `remove_without_manifest_refuses`、`a_directory_without_manifest_is_not_overwritten`。

### G81. 落盘路径要逐段校验，不能只做字符白名单
- **现象**：`references/../SKILL.md`、`C:\x`、`a:b`（NTFS 数据流）、`a\b`（Unix 上只是普通字符）
  都可能绕过“含 `..` 就拒绝”这种单点检查。
- **原因**：不同平台对分隔符与盘符的解释不同；字符串比较不等于路径语义。
- **规则**：用 `std::path::Component` 逐段判定：只接受 `Normal`，拒绝
  `ParentDir/RootDir/Prefix`；显式拒绝 `\`、`:`、NUL；拒绝覆盖入口 `SKILL.md`
  与清单 `.metis-hub.json`。对应测试：`safe_skill_path_rejects_traversal_and_reserved_names`。

### G82. front-matter 的 flow 数组写回后会被规范化
- **现象**：`build_meta` 写 `hub-skills: [a@1.0.0]`，保存后重新读取变成
  `["a@1.0.0"]`（解析器把它当列表重新渲染），按原字符串比较会误判“内容变了”。
- **原因**：`metis-persona` 对 `[...]` 会解析成列表，未知键保存的是列表视图的 `raw`。
- **规则**：跨“写入 → 重读”比较 provenance 时，比较**语义**（是否包含某个值）
  或直接比 `hub-hash`/`hub-version`，不要比 flow 数组的原始文本。
  对应测试：`imports_expert_and_installs_linked_skills`（用 `contains` 断言）。

### G83. 详情缓存 10 分钟：改完 Hub 立刻重导会看到旧内容
- **现象**：同一个 expert 在 Hub 上更新后，紧接着重导，`identical` 而不是 `overwritten`。
- **原因**：详情缓存的新鲜期是 10 分钟；导入默认走缓存，不重新请求。
- **规则**：需要拿最新版本时显式 `refresh`（CLI/UI 的“刷新”），或等缓存过期。
  测试里模拟“Hub 内容变了”必须带 `refresh: true`，否则测的是缓存而不是导入逻辑。

### G84. 把本地路径写进提示词时，分隔符会混用
- **现象**：用 Git Bash 的 `/tmp/x` 作为 `--home`，导入后正文里的技能路径是
  `C:/Users/…\skills\…`：前缀是正斜杠，拼出来的部分是反斜杠。
- **原因**：`Path::display()` 保留传入时的分隔符；Windows 的 `PathBuf` 同时接受 `/` 和 `\`。
- **规则**：写进**用户可见内容**（尤其是给模型读的本地路径）之前，Windows 上统一成 `\`；
  路径本身仍然合法，但可读性和可粘贴性更好。
  对应测试：`display_path_uses_the_platform_separator`。

### G85. 列表每行都有同名「详情」按钮 → `AMBIGUOUS_TARGET`
- **现象**：真实窗口里点列表第一行的「详情」，`agent-desktop` 返回
  `AMBIGUOUS_TARGET`；读屏用户听到的也是几十个一模一样的“详情”。
- **原因**：可见文字相同，**无障碍名字**也相同；ref 无法唯一重识别。
- **规则**：重复行里的操作控件必须把行标识写进 accessible name
  （`详情：<名称>`），可见文字可以保持简短：
  ```rust
  let link = widgets::link(ui, "详情");
  link.ctx.accesskit_node_builder(link.id, |node| node.set_label(format!("详情：{}", item.name)));
  ```
  对应实现：`screens::hub_card`；真实窗口验证通过。

### G87. 详情内联 + 长结果列表会把整页撑长
- **现象**：详情放在列表卡片下面，打开一条就把列表顶走；20 条结果时整页很长，
  分页控件被推到很远，窗口里看着像"没有分页"。
- **原因**：详情和结果都参与页面布局，高度随内容线性增长。
- **规则**：详情用 `Area + Order::Foreground` 独立浮层（与执行器详情同一套模式），
  浮层内容自己的 `ScrollArea` 限高；结果列表 `ScrollArea::max_height(480)`，
  分页控件留在滚动区外。对应测试：`the_hub_detail_overlay_paints_only_when_selected`、
  `the_hub_list_is_height_bounded_and_scrolls`。

### G88. 人设正文是 Markdown，别用纯文本 Label 展示
- **现象**：详情里把 `prompt` 原样塞进 `Label`，`# 标题`、`**加粗**`、列表全部变成原始符号，
  用户以为远端内容坏了。
- **原因**：人设正文是 Markdown；纯文本控件不会解析它。
- **规则**：展示层用 `egui_commonmark` 渲染 `prompt` / `knowledge[].text` / `notes`；
  **存储层仍原样保存原文**，渲染只发生在 UI。对应实现：`hub_detail_content`；
  真实窗口验证能看到 Markdown 标题。



### G86. `#[serde(flatten)]` 加上同名字段 → 重复 JSON 键，反序列化必坏
- **现象**：`HubDetail` 里 `item: HubSummary` 有 `source`（条目来源），外层又有一个
  `source: DataSource`（网络/缓存）。序列化出两个 `"source"` 键，UI 用
  `serde_json::from_value::<HubDetail>` 报 `expected value`。
- **原因**：`flatten` 只摊平字段，不解决命名冲突；JSON 允许重复键，serde 的行为不可依赖。
- **规则**：`flatten` 的外层字段**不能**和内层字段同名；用 `#[serde(rename = "dataSource")]`
  区分，并加一条 **round-trip** 测试（`page_and_detail_round_trip_through_json`）钉住。
